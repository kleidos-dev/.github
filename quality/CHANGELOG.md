# Quality kit changelog

One entry per release; each says what can turn a green repository red. The rules, and how a repository takes a release, are in [`docs/quality.md`](../docs/quality.md).

## 3.1.0 (2026-11-24)

The open points of the second review of 3.0.0 (3 and 5), and what a review of this release found. MINOR, by [`docs/quality.md`, "Versions"](../docs/quality.md#versions): every rule added is one every repository of the list already passes, and it can add findings only where a repository switches a tool off from its tree. The impact preview finds the same counts as 3.0.0 in every repository, public or private, as their `main` stands (boards 0 and brand 0 in the run form; after the mechanical switch cla 3, social 5, agents 8, posts 1, qa 4, videos 3; the 2.x copies 0 everywhere). It is a security fix, the exception to moving `v3` at most once a week, so it may follow 3.0.0 within the week: before it, a tree could switch off a default gitleaks rule with no waiver and `refresh` could write a workflow.

- The jobs that hold a secret or a token are held by what their steps do, not by their names (`test_secret_isolation.py`): what each action is told (`persist-credentials: false` on the checkout and no other ref, repository or token; no cache for `setup-python`; only the server's address in an action's environment); the keys a step may have (`name`, `id`, `uses`, `with`, `env`, `run`, `timeout-minutes`: no `shell`, `working-directory` or soft failure but the one listed, no condition but the three listed); the one-line scripts word for word; the secret in the last step only, given to the hooks whole; the kit's folder only from the step that fetched it, which takes the repository's tree as the kit only in the kit's own repository; the job's own permission `contents: read`. The conditions that decide what runs (`deny` and `commits` in `quick.yml`, `KLEIDOS_DENY_OPTIONAL`, the comment job, each listed step condition) are evaluated case by case by a reader of GitHub's expression language in the tests (`quality/tests/expressions.py`).
- `python -I` for every `python -m` and `python -c` of a kit job, whose working directory is the repository's tree: a `pip.py` or `json.py` planted there no longer runs in place of the module. `test_entry_workflows.py` holds it.
- The release check (`sync.py --release-check`) refuses a release tag that is lightweight or carries no PGP or SSH signature, and with `--online` (this repository's CI) one whose signature GitHub does not verify; and any tag named like a branch (`v3`, `main`), which GitHub would resolve first. When a branch takes a release tag's name, it says to delete the branch: a release tag is never deleted or moved.
- `tools/ecosystem.py land` masks a version only where it is a package's (its name, then one of pip's operators, and each further bound a comma adds to it), and leaves to a person any changed line that names a floor or an index, in any block of any hunk, added or taken away: `fail_under`, `--cov-fail-under`, `requires-python`, `python_requires`, Poetry's `python`, uv's `required-version`, `--index-url`, `-i`, `--extra-index-url`, `--find-links`, `--trusted-host`, `-c`, and in `package.json` the engines, `registry` and `packageManager`. A changed version line of `package.json` names a package one of Dependabot's commits says it updates, so no engine of any name (`vscode`, `deno`) moves.
- `tools/ecosystem.py refresh` writes nothing under `.github/` or at `.pre-commit-config.yaml` (workflows, actions, Dependabot's settings, the hook list): a path is compared as a file system that folds case and Unicode compatibility forms reads it (`workflowſ`, `workﬂows`), and by what the file system resolves it to. A path in git's folder is found the same way.
- The owner's e-mail beside his name is found in a `mailto:` link too.
- A tool switched off from the tree: a step-level `continue-on-error` (`tool = "ci"`); an `ignore` of `.github/actionlint.yaml` (`tool = "actionlint"`, new); a typos configuration other than the top `.typos.toml` (`typos.toml`, `_typos.toml`, a nested one, a typos table in a `pyproject.toml` or `Cargo.toml` however the TOML spells it), an `extend-exclude` of every file with an extension (`*.*` too), `check-file` or `check-filename` false, an `extend-ignore-re` pattern that leaves no word to check (`.`, `[a-z]`), an identifiers or words pattern found in every word (`tool = "typos"`, new); a `.markdownlint*` configuration in a folder or a second one at the top (`tool = "markdownlint"`) are weakenings that need a waiver. A second zizmor configuration, a gitleaks allowlist whose `paths` or `regexes` find everything (`\.` too), a gitleaks rule of the tree whose id is not the repository's own (`kleidos-…`: gitleaks merges it into the default rule of that id), a SonarCloud suppression (`sonar.issue.ignore.*`) and a Sonar exclusion of every file (`**/*.*` too) are refused with no waiver. This repository waives its one soft step, the comment job's fetch of a result that may not be there.

## 3.0.0 (2026-11-24)

The kit is run, not held (owner, 2026-11-24): a repository calls it by its name, `@v3`, and holds none of its code. MAJOR, and additive: a repository that holds 2.x copies keeps running the commit it recorded, its drift notice answers "not behind", and nothing of it changes until its own switch. The impact preview found no problem in the 2.x copies of boards, brand, social, cla, qa, videos, agents and posts brought to this release; after the mechanical switch, only what a person edits in the same pull request: the license lines (boards, brand, social, cla, agents), the paths of removed kit files that `AGENTS.md` still names (every one), and three `pins` waivers that have nothing left to waive (agents).

- The entry workflows `quick.yml`, `check.yml` and `sonar.yml`, called at the branch `v3`. Each job fetches the kit at the commit of the workflow it is in and says which in its summary. Only `quick.yml` takes a secret, by name, and gives it to one job, `reusable-deny.yml`, which runs the repository's own hooks that `deny-hooks` names and nothing of a third party before them.
- The gate: a repository's own last job, `✅ Check`, needs every other job, always runs, and fails unless each succeeded or was skipped with leave (`MAY_SKIP`). The check holds it to the model word for word, refuses a second one, refuses what could steer its step (`env`, `defaults`, a matrix, a soft failure), and refuses any workflow whose token can write checks or commit statuses. What it cannot prove, and the merge procedure that follows from it, are in [`docs/quality.md`, "Merging"](../docs/quality.md#merging).
- The hooks `kleidos-kit`, `kleidos-commit-msg` and `kleidos-mypy` (`.pre-commit-hooks.yaml`), scripts that start on Python 3.9 and run on one that can, or say in one line what to install.
- The run form of the check (`run_form.py`): the record of the base configurations (schema `kleidos.vendored-copy/1`), their bytes against the ones released, no kit code or block marker left, the reference at `v3` and nothing else (zizmor's policy takes any name, `@main` included), grants and secrets, the canonical third-party hooks unweakened, Dependabot's `pre-commit` entry. A pin that is behind is a note there, never a problem.
- The kit owns the commit-message checker (`hooks/check_commit_msg.py`, as `kleidos-dev/agents` last had it); CI runs the kit's, and no repository copies it.
- The owner's copyright statement is year and name only, in the license texts too (`spdx_headers.py`): no e-mail with the name in any file, however either is written. A problem in the run form; a note where 2.x copies are still held.
- `tools/ecosystem.py` with its declared list: the report of what is behind, broken or undeclared (its public half weekly, in `ecosystem.yml`), the preview, the refresh of a copy, and the landing of Dependabot's pull requests under guards. The weekly `📦 Pinned versions current` job is gone: a kit pin with a newer release is an amber line there.
- `tools/kit_switch.py`: the mechanical part of a repository's switch.
- The organization norm on tests ([`docs/quality.md`, "Tests"](../docs/quality.md#tests)), in the organization rules too, which a repository links from now on instead of carrying them as a block. The kit's code is measured whole and held by `coverage_floor.py`.
- The check refuses the scanner's own settings in `sonar-project.properties` (`sonar.scanner.*`, `sonar.host.url` and three more).
- Releases are tagged `v<VERSION>`; `sync.py` writes in this repository only, its release check is red on `main` until the branch is at the tag's commit, and it and the drift know both prefixes; `--drift` answers "not behind" for a 2.x commit, or one it cannot read.
- `SonarSource/sonarqube-scan-action` 8.5.0 to 8.5.1.

## 2.2.0 (2026-11-23)

The pin rule now sees the pins a repository takes from a git submodule. social installs brand's stack through `-r brand/requirements.txt`, and its submodule sat one brand commit behind, so social kept charset-normalizer 3.5.2 after brand moved to 3.5.3; no rule saw it. MINOR: every repository passes it at release (social is the one repository with a submodule, and it records brand's tip since social#13); it turns a repository red later only when the submodule's branch moves a pin the repository has not taken.

- `check_quality.py`, rule `pins`: a requirements or constraints file (any `*.in`, or a `*.txt` named for them or under `requirements/`) that includes (`-r`, `-c`) a file of a submodule must pin, through it and every file it includes, what that file pins at the tip of the submodule's branch (`.gitmodules`' `branch`, the repository's current branch for `branch = .`, else the default one). With the kit (the CI's `--kit`) it fetches the upstream into a scratch repository (depth 1, no blobs but the files read) and compares; a pin the tip adds, drops or moves is a finding, waivable with a `below-latest:` reason beside the include and `what = "submodule:<path>@<short commit>"`, and an upstream that cannot be fetched is a finding too. A pin under an environment marker is compared per marker; a `branch` that is not a plain branch name is refused, and the URL follows `--`, so nothing from `.gitmodules` reaches `git fetch` as an option. Offline, a submodule waiver is not reported unused. Offline (the pre-commit hook) it fetches nothing and notes it.

## 2.1.0 (2026-11-23)

Container images join the pin rule. Nothing turns a green repository red: the only image the kit knows, `kicad/kicad`, is already pinned by its 10.0.8 digest in boards and brand, and no other repository runs a known image.

- `LATEST_IMAGES` (`check_quality.py`): the newest stable tag of `kicad/kicad`, 10.0.8, and the digest it names, `sha256:3f4a01786dfbe803a65f345c3342b765db9add913f5e9448f8356793714ddc34`. Every workflow `image:` (a job's `container:` or a service) or `container:` shorthand of a known image is pinned by that digest with its tag in a comment (`kicad/kicad@sha256:… # 10.0.8`); a tag alone, a digest with no tag and the newest tag with another digest are findings no waiver clears, and an older tag is held like any other pin (`below-latest:` and a waiver, `what = "image:<name>:<tag>"`).
- The weekly `📦 Pinned versions current` job (`latest_releases.py`) also reads each known image's newest stable `x.y.z` tag on Docker Hub and the digest it names, and turns red on a newer tag or on the same tag pushed again. Dependabot cannot do it: its `docker` ecosystem reads Dockerfiles and Kubernetes manifests, not a workflow's `container:`.

## 2.0.0 (2026-11-23)

Every pin at the latest stable release (owner, 2026-11-23). MAJOR: the new pin rule turns red every repository that names a Python below 3.15 (agents, boards, qa and videos, by the impact preview), and the kit's scripts now need Python 3.14 or newer, so a repository takes this release together with its move to 3.15 (or a written reason and a waiver where it truly cannot move).

- The pin rule (`check_quality.py`, rule `pins`): every Python a repository names (`.python-version`, ruff `target-version`, mypy `python_version`, `requires-python`, a workflow's `python-version`, and the matrix key a `python-version: ${{ matrix.<key> }}` reads), every `uses:` of an action the kit pins and every `rev:` of a hook repository the kit's blocks use must be at the newest release the kit knows (`LATEST_PYTHON` 3.15, `LATEST_ACTIONS`, `LATEST_HOOKS`, held equal to the kit's own pins by a kit test). One that cannot move carries its reason beside it after `below-latest:` and a waiver, `tool = "pins"`; without the reason it is a finding no waiver clears, and so is a known hook pinned by a bare commit SHA with no tag beside it.
- The weekly `📦 Pinned versions current` job ([`latest_releases.py`](latest_releases.py)) replaces `📦 Pinned release binaries current`: it compares the kit's Python, actions, hook revs, PyPI tools and `tools.lock` binaries with upstream and turns red on a newer stable release.
- Bumped: zizmor 1.33.0 to 1.33.1 (PyPI tool and the `zizmor-pre-commit` hook of the `pre-commit-actions` block), charset-normalizer 3.5.2 to 3.5.3; `requirements-tools.txt` is compiled for Python 3.15. Every other tool, action, hook and binary was already at its latest release, each SHA checked against its tag's commit and each binary's SHA-256 against its release's checksum file.
- The kit's own Python is 3.15: ruff `target-version = "py315"` and mypy `python_version = "3.15"` here, and `reusable-lint.yml` (its default), `reusable-reuse.yml`, `reusable-secrets.yml` and `reusable-quality-drift.yml` run 3.15 instead of 3.14. `ruff format` at that target drops the parentheses of multi-exception `except` clauses (PEP 758), which Python 3.14 and newer read.

## 1.1.0 (2026-11-23)

mypy groups, for a repository whose scripts sit in plain folders that repeat file names (a `score.py` in each video's folder), where one mypy run stops at "Duplicate module named". Nothing turns a green repository red: without groups every repository runs the same bare `mypy` as before, and the new duplicate-module check reports only what that run already fails on (the impact preview found nothing in boards, brand, social, cla, qa, agents and posts).

- A repository may declare `[[tool.kleidos-quality.mypy-groups]]` in its `pyproject.toml`: each group a `name` and the `files` (folders, files, or globs such as `music/*.py`) of one mypy run. A group sets nothing else, so every run reads the same `[tool.mypy]` and the kit's strict block; with groups, `[tool.mypy]` sets no `files`.
- `quality/mypy_groups.py`, copied by the python profile to `.github/quality/mypy_groups.py`, runs mypy once per group, each with a cache of its own, and every group even after one fails; without groups it runs a bare `mypy`. The mypy hook of the `pre-commit-python` block now runs it (`python3 .github/quality/mypy_groups.py`).
- `reusable-mypy.yml` runs it with `--github`: a fold per group in the log, an error annotation per failing group, and a table of every group in the job summary.
- `check_quality.py` holds every tracked Python file to exactly one group (or, without groups, to `files` as before), refuses a group key other than `name` and `files`, a bad name or path, `files` beside groups and any other `[tool.kleidos-quality]` key (no waiver), reports a group folder that holds no Python file, and reports two files of one mypy run that mypy would name the same module.

## 1.0.0 (2026-11-23)

The first release, tagged `quality-v1.0.0` at its merge commit on `main`: `sync.py --write` records only a release tag on `main`. A repository that adopts it gets:

- ruff with the kit's bug-finding rule set and `ruff format`; mypy strict (phonometry's floor) over every Python file, with every error fixed and no baseline.
- actionlint, zizmor (every `uses:` pinned by SHA, the `self-repository` audit off while actionlint rejects `$/`), shellcheck at warning severity, and the CI conventions checked.
- typos (US English), gitleaks over the tree and the history with the default rules and the MAC rules, OSV-Scanner as a gate, Dependabot coverage.
- `reuse lint` and the licensing header rule: both REUSE lines, copyright first, with the year of the file's first commit and no e-mail, in every file that can carry a comment.
- The Markdown no-wrap rule and markdownlint's broken-table rules.
- ESLint and tsconfig bases for TypeScript, a clang-tidy base for C++.
- Reusable workflows for lint, licensing, types, Python tests, OSV, secrets, SonarCloud, the commit-message gate and its comment, and the weekly drift notice.
- `check_quality.py`, which checks the copies, the blocks, the kit workflow references and the conformance of the repository's own configs, with waivers for the weakenings it allows. A kit workflow counts as called only from a job that runs on every pull request and push to `main`; the lint caller's `skip` may not name a kit hook; `.github/quality/` holds only the kit's copies; `[tool.mypy]` takes an allowlist; a `.python-version` (python), a Dependabot `cooldown`, the ESLint workflow (ts) and a local clang-tidy job (cpp) are required.
- The header rule held at the top of each file, with an owner line, the first-commit year in UTC or the year before (squash merges across the new year), Astro headers in the front matter, and every text file of an unknown format named in `REUSE.toml`.
- The commit-message checker the CI runs recorded against kleidos-dev/agents (`.github/commit-check/SOURCE.json` and its digest test); the tool pins are not copied into repositories.
